# Multi-Agent Cab Dispatch using Reinforcement Learning

A research prototype implementing the AAI project proposal: a decentralised multi-agent cab-dispatch system in a 5×5 simulated city with 8 learning agents.

## PPT-aligned scope

- 5×5 zone grid and fixed fleet
- 8 cab agents in the pilot configuration
- Full 24-hour (1,440 minute) episodes
- Stochastic time-varying demand with morning/evening peaks
- Airport demand hotspot
- Local observations plus neighbour idle/request counts
- Maximum pickup radius and rider cancellation timeout
- Configurable driver shift
- Nearest-Cab Greedy baseline
- Zone-Balancing baseline
- Parameter-shared DQN, γ = 0.95
- Experience replay and target network
- Hybrid individual + city-wide shared reward
- Held-out multi-seed evaluation
- Peak/off-peak analysis
- Fleet-size sweep: 4, 8, 12, 16 cabs
- Metrics: wait, pickup distance, service rate, cancellations, empty driving, utilisation, earnings, earnings fairness and convergence
- VDN cooperative value-decomposition extension
- Research dashboard with a clearly labelled illustrative animation

## Train the proposed DQN

The training workflow defaults to 360 complete simulated days. The committed validation run uses 120 days; it is not evidence of convergence:

```bash
python -m backend.train --episodes 360 --day-minutes 1440 --fleet-size 8 --learn-every 4
```

## Run the research benchmark

```bash
python -m backend.experiment --episodes 5 --fleet-sizes 4,8,12,16 --day-minutes 1440
```

This evaluates identical seeds across the rule baselines and DQN, then reports mean and population spread for the research metrics.

## VDN extension

`backend/agents/vdn.py` implements a centralised-training/value-decomposition extension in which local cab Q-values are summed into a joint team value while execution remains decentralised. It is an extension to the core DQN experiment, not a claim that VDN already outperforms DQN.

## Demand calibration

The simulator currently uses a clearly labelled synthetic demand prior. Its time-of-day and airport-hotspot parameters are deliberately exposed as a calibration surface for future fitting to public taxi-trip statistics. The repository does not claim that the current synthetic rates are measurements from a real city.

## Results integrity

The dashboard consumes `results/experiment_results.json` and `results/training_curve.json`. Results are generated by the Python simulator and benchmark scripts. No performance number should be manually entered into the dashboard.

## Correctness review against the supplied PPT (12 October 2026)

The code implements the proposal's 5×5 grid, 8-agent pilot, one-minute travel,
24-hour days, synthetic peaks/airport prior, driver shift, local sensing,
parameter-shared DQN (gamma 0.95), replay/target networks, hybrid reward,
nearest-cab and historical-prior zone-balancing baselines, multi-seed fleet
sweeps, and peak/off-peak evaluation. VDN is implemented as an experimental
extension. QMIX, real taxi-data calibration, ride pooling, EV charging and
pricing remain future work, as allowed by the proposal.

Corrections made in this review:

- Pickup and passenger travel now advance physically by one zone per minute.
  Pickup time, drop-off time, cab status and fare follow those transitions.
- Nearest-cab dispatch reserves the closest eligible cab for each request.
  The rule dispatcher sees all open requests; DQN executes with local sensing.
- Observation direction slots retain north/south/west/east meanings at edges.
  Local sensing is Manhattan radius 1; maximum dispatcher pickup radius is 3.
- DQN and VDN bootstrap only over valid next actions.
- Rewards include active idle cost. Metrics include cancellation rate, pending
  requests, actual empty/loaded distance, pickup distance and earnings fairness.
- Service and cancellation rates divide by all generated requests. Pending
  requests at the episode boundary remain unserved, so these rates need not
  sum to one. Average wait covers picked-up riders, including trips in progress.
- Peak/off-peak groups partition the entire day and include DQN when a valid
  checkpoint is supplied. Each method uses identical held-out demand seeds.
- Result metadata records actual training length, model hash and evaluation
  seeds. Old simulator checkpoints must be retrained.
- The browser animation uses illustrative rules. Its decisions and inspector
  are not outputs from the trained network. Invented Q-value bars were removed.
  Benchmark metrics are Python outputs and are independent of animation demand.

`configs/default.json` describes the reference design. CLI arguments and the
`CabDispatchEnv` constructor currently configure runs; that JSON is not loaded
automatically. Fares use synthetic units. Overnight demand continues while the
fleet is off shift (06:00–22:00), so overnight cancellations affect full-day
results. Fairness is a clipped 1 minus coefficient-of-variation score. These
choices must accompany reported results.

The supplied PPT is a proposal, not measured performance evidence. Its first
slide lists Kavya Gala (E015), Aarya Shah (E011), and Om Parekh (E031), but the
last slide lists Kabeer Bilal (E040), Dev Sheth (E054), and Madhav Mehta (E057).
Reconcile those team details before presenting. The PPT itself was not edited.

Validation: `python -m pytest -q` exercises timing, sensing, assignment,
timeouts, accounting and DQN/VDN target masking. A short training run and
held-out benchmark verify execution, not superiority or convergence. Run the
360-day workflow and assess learning curves before making final claims.


## Predictive coordinated dispatch extension

The proposed operational improvement is `Predictive Coordinated Dispatch`.
It adds a central coordination layer to the original local DQN research core.
This extension is forecast plus optimisation, not a renamed RL algorithm. The
original parameter-shared DQN remains a separate comparison. Strictly local,
decentralised execution remains a limitation/future extension of this planner.

1. Fit smoothed hourly zone-arrival rates using training demand days only.
2. Jointly match available cabs to current requests: maximise the number of
   feasible matches, then minimise pickup cost with a small age priority.
3. Idle cab agents propose adjacent moves or waiting. Sequential reservations
   account for peers' planned positions, reducing clustering. Choose moves
   that improve forecast-weighted pickup coverage enough to offset movement.
4. Advance the same one-minute simulator with the same radius, fleet, shift,
   timeout, fares and demand sequence used by every baseline.

The model never reads the evaluated day's future demand. The forecast uses
seeds 42–171. Movement cost 0.05 minimised the validation score `avg_wait + empty_distance / 2000` (an explicit synthetic trade-off, not a fuel-price estimate). It was selected on validation seeds
200000–200004, separately from new held-out seeds 300000 onward. The previous
100000-series test was not reused for these improvement claims. Baseline
matching and forecast coordination both have central information. Plain DQN
retains local information, so the comparison cannot isolate the effect of RL
versus extra information. `Coordinated Matching` is the no-repositioning
ablation. The `Zone Balancing` baseline is unchanged.

DQN training also changed: exploration now decays over training episodes,
and off-shift forced-WAIT transitions do not fill replay or consume learning
updates. This fixes the original exploration collapse before the first shift.

Reproduce the extension and the fresh evaluation:

```bash
python -m backend.coordination.predictive --seed-start 42 --days 130
python -m backend.tune_coordination  # optional: reproduce validation selection
OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 python -m backend.train --episodes 120
OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 python -m backend.compare_improvements --episodes 20
```

The final command produces full-day, 4/8/12/16-cab benchmarks for five methods,
peak/off-peak metrics, per-seed results, paired 95% t intervals, and an 8-cab
stress test with 1.5× arrival probabilities. Results are conditional on one
training run and synthetic demand. Confidence intervals reflect variability
across demand days, not model-training restarts. Overnight shift restrictions
limit the maximum full-day service rate for all methods. A lower wait among
served riders alone is not proof of a better service: compare service rate,
cancellations, earnings and empty driving together.

Background sources (design context, not evidence for our measured gains):

- Lin et al., KDD 2018, [Efficient Large-Scale Fleet Management via Multi-Agent
  Deep Reinforcement Learning](https://www.kdd.org/kdd2018/accepted-papers/view/efficient-large-scale-fleet-management-via-multi-agent-deep-reinforcement-l).
- [SciPy linear assignment documentation](https://docs.scipy.org/doc/scipy/reference/generated/scipy.optimize.linear_sum_assignment.html), used for the joint matching solver.


The measured comparison, uncertainty and scaling trade-offs are in
[results/improvement_summary.md](results/improvement_summary.md), generated
from the recorded JSON outputs. Improvement claims apply to the forecast
coordination extension. They do not establish DQN superiority or universal
dominance: nearest-cab dispatch uses less empty driving, and zone balancing
has lower wait at 16 cabs. The 8-cab pilot shows the intended wait/empty-driving
improvements against zone balancing, while its service-rate difference is
not statistically established. The higher-demand stress scenario supports
lower wait and lower empty distance against zone balancing without refitting.


## Incoming-aware controller update

The latest optional controller, `Incoming-aware Coordinated Dispatch`, improves
planning by considering cabs' known drop-off zones and time remaining until
availability. It also prioritises currently unmatched requests by wait age.
This uses operational trip information, not future demand from a test day.
The previous predictive controller remains in the benchmark as an ablation.

Parameters were selected on a new validation split (500000–500004), using the
same waiting/empty-distance score and preferring no service-rate loss. The
selected configuration is recorded in `models/incoming_config.json`; validation
outputs are in `results/incoming_validation.json`. New normal test seeds begin
at 600000 and stress seeds at 700000. Earlier test seeds were not reused for
this update's improvement claims.

```bash
python -m backend.tune_incoming
OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 python -m backend.compare_incoming --episodes 20
```

[Latest measured results](results/incoming_summary.md) include the comparison
against the previous controller, baselines, confidence intervals and stress
test. The earlier `improvement_summary.md` refers to the prior 300000-series
experiment; the latest `experiment_results.json` is the new 600000-series run.
As before, the controller is a central forecast/optimisation extension, and
its improvements must not be attributed to the separate plain DQN model.


The incoming-aware configuration was chosen for its combined waiting/empty
travel objective. A lower objective does not imply each metric dominates the
previous controller. The latest report exposes any waiting-time trade-off
alongside the empty-distance saving. Tests cover use of known drop-off timing,
queue priority without double-counting matched riders, and absence of future
arrival access. Both controller versions remain separately selectable.

## Interactive policy viewer (October 2026)

Live dashboard: https://aai-project-dashboard.onrender.com

The viewer opens at 07:00 and waits for the Start button. Playback advances one
simulated minute per 1.5 seconds. Pause/resume, single-step, slower pace, restart,
and a full-day timeline make decisions inspectable. Choose the PPT baselines
(nearest cab or zone balancing) and fleets of 4/8/12/16. Each uses the same
synthetic demand seed, 810000. The original forecast controllers remain in the
research comparison and Python backend.

Playback comes from actual Python simulator executions, with Q-values computed
from `models/dqn_latest.pt`. It does not run training or model inference in the
browser. Decisions on a frame apply to the next minute. Busy cabs continue their
assigned routes; they cannot choose a new dispatch action until available.
The highlighted zones show the selected cab's radius-one local view. Baseline
central dispatchers can see more information, as documented above.

Rebuild deployable data after changing models, simulator or benchmark outputs:

```bash
OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 python -m backend.export_replay
python scripts/bundle_research.py
python -m http.server 8000 --directory frontend
```

All browser data lives in `frontend/data`, inside Render's `frontend` publish
path. This fixes the previous 404s for `/results` outside the published folder.
The training workflow now republishes this bundle and replays alongside models.
Research averages and single-seed playback statistics are visibly separate.
Network failures show an explicit retry message rather than silent blank cards.
